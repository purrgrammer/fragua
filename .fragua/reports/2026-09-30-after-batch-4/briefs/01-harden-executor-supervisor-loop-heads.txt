Wrap every per-run and per-tick store call in the two long-lived daemon fibers in try/catch so one malformed row or transient store error skips that run instead of killing the process. Problem: packages/daemon/src/executor.ts runExecutor while-loop calls wakePending(opts.store), processOperatorActions(opts.store), and opts.store.claimNextRun(maxConcurrentRuns) with no try/catch; wakePending and processOperatorActions re-throw any non-ConcurrencyError, which unwinds runExecutor, is caught in startDaemon as stoppedReason='error', and exits the process. Separately, packages/daemon/src/supervisor.ts tick loop calls opts.store.getUnappliedIntents(runId) in the intent-detection for-loop and opts.store.getState(runId) in the stuck-node watchdog for-loop, both unguarded; a throw rejects the supervisor async IIFE, stops the 5s heartbeatDaemonLock, and lets the daemon_lock TTL lapse so a reaper takes over — contradicting the file's stated 'the supervisor must never crash the daemon' invariant. Build: (1) In runExecutor, guard the wakePending and processOperatorActions calls so a non-fatal store error is logged (daemon.sweep_error style observability or console.error) and the loop continues to the next tick; keep claimNextRun's existing behaviour but ensure its failure does not skip the backoff. (2) In supervisor.ts, wrap the getUnappliedIntents call and the getState watchdog call in per-run try/catch that logs and continues to the next activeRun, leaving heartbeat and onSteer as-is. (3) Define which errors are genuinely fatal (e.g. SQLITE_CORRUPT) and let only those propagate. Tests: add a daemon test that injects a throwing store.getState/getUnappliedIntents for one run and asserts the supervisor fiber stays alive and heartbeats; add an executor test where processOperatorActions throws a non-ConcurrencyError and assert the executor loop continues and other runs still dispatch. Docs: update ARCH §1.3/§6 if the tick error-handling contract is newly documented. Constraints: do not swallow ConcurrencyError differently than today (it is already skip-and-retry); route transitions still only through store writes; no filesystem coordination.
